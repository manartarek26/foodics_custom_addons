0. One-time setup

This assumes foodics_base, foodics_mock and foodics_accounting are installed. If you haven't connected to the mock server at all yet, do that first - see the root README.md, section "Test the whole flow right now, with no real Foodics account", steps 1-4. In short:

  1. Create a Foodics Mock > Fake App.
  2. Create a Foodics > Connection pointing its Custom API/Authorization Base URLs at the mock server, and authorize it.
  3. Copy the Connection's Webhook URL into the Fake App's Webhook URL field - this is what lets the mock actually deliver webhooks to Odoo, and every case below needs it.
If you change any Python file in foodics_mock or foodics_accounting (or pull an update that does), restart the Odoo server process before testing. Controller/model code is only read once, when the process starts - editing a .py file on disk does not hot-reload into an already-running server, unlike views/data which a module upgrade (-u, or Apps > Upgrade) does pick up. A stray 404 with a bare "NOT FOUND" body (not a JSON message) almost always means this.

On the Connection form, under the Accounting group, set:

FieldSuggested test value
Sales JournalAny Sales journal
Default CustomerAny contact - used for walk-in (no-customer) orders
Auto-post invoicesOn (default) - to test the full automatic path first
Auto-register paymentsOn (default)

1. Master data: taxes & payment methods

Do this once, before firing any orders - every case below depends on it.

  1. On the Connection, click Sync Taxes. The mock returns one canned tax, VAT 15% (Mock).
  2. On the Connection, click Sync Payment Methods. The mock returns two: Cash (Mock) and Card (Mock).
  3. Open Foodics > Tax Mapping and set Odoo Tax on the VAT 15% row to a real 15% sale tax (create one if your chart of accounts doesn't have one).
  4. Open Foodics > Payment Methods and set a Odoo Journal on both rows - e.g. Cash → your Cash journal, Card → your Bank journal.

Leave one thing unmapped for now - Cases G and H below deliberately test what happens when you forget this step.

Building test orders: Foodics Mock > Mock POS Orders

Every case below uses this same tool. It represents a POS sale you build by hand - branch, product lines, an optional charge, payments, an optional customer - then fires it at foodics_accounting exactly the way a real Foodics till would: as an order.updated (or customer.order.updated, if a customer is set) webhook, carrying the same order shape GET /orders returns.

ButtonWhat it does
Send order.created Fires the order while still Pending - not accounting-relevant, just confirms the event reaches foodics.webhook.log and is correctly ignored.
Close & Send order.updated Sets status to Closed (4) and fires the webhook - the main path.
Close WITHOUT Webhook Sets status to Closed but does not call the webhook - for testing the pull cron/button as the backstop.
Return This Order Rings up a brand-new order (its own id/number) as a full return of this one, status 5, and fires its webhook - matching how Foodics itself models a return.
Resend Update Re-fires order.updated with the current data - for testing replay safety.
A real till won't let you close an order until payments add up to the total - this tool enforces the same rule (a warning banner appears, and Close & Send order.updated is blocked, until Payments equals Total Price on the Lines tab).

2. Case A - the happy path

Core One product, one cash payment

  1. Create a Mock POS Order. Branch: Main Branch. Leave Customer empty (walk-in).
  2. Lines tab: add one line, product Burger, quantity 1 (unit price/taxable auto-fill to 28.0 / taxable).
  3. Payments tab: add one payment, method Cash, amount = the Total Price shown on the Lines tab (32.2 for one Burger at 15% VAT).
  4. Click Close & Send order.updated.
Expect: a new record under Foodics > POS Orders, state Invoiced, with a linked Invoice already Posted and Paid. Open the invoice - one line ("Burger"), 15% tax, total matching. The Foodics Order smart button on the invoice links back to this record.

3. Case B - split payment

Payments Two payment methods on one order

  1. New Mock POS Order, two lines (e.g. Burger x1, Pepsi x1).
  2. Payments tab: add two rows - part Cash, part Card - that together equal the total (split it any way you like).
  3. Close & Send.
Expect: state Invoiced, invoice Paid. Open the POS Order's Payments tab - two rows, each with its own Odoo Payment linked, both reconciled against the same invoice.

4. Case C - mixed taxable/non-taxable lines + rounding

Taxes Milk is non-taxable by default

  1. New Mock POS Order, two lines: Pepsi (taxable, auto-checked) and Milk (auto-unchecked - it's the one canned "non-taxable" product).
  2. Set a small Rounding Amount on the Lines tab, e.g. 0.1.
  3. Pay the exact total shown (which now includes the rounding), Close & Send.
Expect: the invoice has a tax line only on Pepsi, a plain untaxed line for Milk, and a separate "Rounding" line for the rounding amount. Total still matches exactly (this is exactly the scenario the automatic total-match check is there to catch if it didn't line up).

5. Case D - service charge

Charges An order-level charge, taxed

  1. New Mock POS Order, one product line.
  2. Under Optional Charge, set an amount (e.g. 5) and leave Charge Taxable checked.
  3. Pay the total, Close & Send.
Expect: the invoice has an extra line named "Service Charge" (or whatever you typed), taxed the same way a product line is.

6. Case E - customer vs walk-in

Customers Named customer creates/reuses an Odoo contact

  1. New Mock POS Order. Fill in Customer Name (and optionally phone/email). Notice the event fired becomes customer.order.updated instead of order.updated once a customer is set.
  2. Add a line, pay the total, Close & Send.
  3. Create a second order with the same customer name+phone, close & send that too.
Expect: both invoices are billed to the same Odoo contact (check res.partner - only one was created, matched by the stable customer id the mock derives from name+phone). An order with no Customer Name instead bills to the Connection's Default Customer.

7. Case F - return / credit note

Refunds A return is a separate order, not a status flip

  1. Take any already-Closed Mock POS Order from a case above.
  2. Click Return This Order. This opens a brand-new Mock POS Order - its own id/number, status Returned - copied from the original's lines and payments, and its webhook has already been sent.
Expect: a second Foodics > POS Orders record, state Credit Noted, linked to a Credit Note (not an invoice) that's posted. Its Payment Status stays unreconciled - credit notes don't auto-register a payment (see the README's "Notes" section for why: Foodics doesn't reliably tell us which original invoice/payment a return corresponds to, so that step is left for manual handling).

8. Case G - unmapped tax → Needs Review

Failure path Missing tax mapping doesn't post a wrong invoice

  1. Go to Foodics > Tax Mapping and clear the Odoo Tax on the VAT 15% row (or delete the row entirely).
  2. New Mock POS Order, one taxable line, pay the total, Close & Send.
Expect: the POS Order lands in state Needs Review, with an error banner explaining the invoice total doesn't match Foodics' total. The invoice was created, but left as a draft - nothing posted, nothing paid.

Now fix it

  1. Re-map the tax under Foodics > Tax Mapping.
  2. Open the draft invoice directly, add the correct tax to its line by hand, and post it (the mapping fix does not retroactively regenerate already-created draft invoice lines - see the FAQ below for why).
  3. Back on the POS Order, click Retry.
Expect: state moves to Invoiced, and the payment(s) get registered/reconciled now that the invoice is posted.

9. Case H - unmapped payment method → Needs Review

Failure path Missing journal mapping doesn't block the invoice

  1. Go to Foodics > Payment Methods and clear the Odoo Journal on the Cash row.
  2. New Mock POS Order, pay with Cash, Close & Send.
Expect: unlike Case G, the invoice does post this time - state is Needs Review, but Invoice Status already shows Posted. Only the payment side is stuck.

Now fix it

  1. Re-map the Cash journal under Foodics > Payment Methods.
  2. Back on the POS Order, click Retry - no manual invoice editing needed this time.
Expect: state moves to Invoiced, a new Odoo Payment appears, reconciled against the invoice.

10. Case I - missed webhook, caught by the pull cron

Reliability The pull sync is the safety net under the webhook

  1. New Mock POS Order, one line, matching payment.
  2. Click Close WITHOUT Webhook instead of the usual close button.
  3. Confirm nothing shows up yet under Foodics > POS Orders.
  4. On the Connection, click Pull Orders (or wait for the "Foodics: Pull POS Orders" scheduled action, every 15 minutes by default).
Expect: the order now appears and gets invoiced, exactly as if the webhook had fired - it went through GET /orders instead of the webhook, into the exact same code path.

11. Case J - webhook replay / idempotency

Reliability Resending the same event must not duplicate anything

  1. Take any already-Invoiced order from a case above.
  2. Note its Invoice number and its Payments tab (Odoo Payment references).
  3. Click Resend Update.
  4. Also try clicking Pull Orders on the Connection right after - it will see this same order again too.
Expect: nothing changes - same Invoice, same Payments, no new records of either kind. This is what "idempotent" means in practice: Foodics is documented to retry failed webhooks up to twice, and the pull cron re-covers the same date range on every run, so this has to hold for the integration to be safe to run unattended.

12. Case K - empty order (defensive)

Defensive An order with nothing to invoice shouldn't crash

  1. New Mock POS Order with no lines at all (this one can't be built through the UI's own close-guard since there's nothing to pay for either - use the developer/ technical list view to force status to 4 and call the webhook method directly if you want to reproduce this exact case, or simply trust the code path: it's covered by an automated check, see the FAQ).
Expect: state Needs Review, error "This order has no lines to invoice." - not a crash, not a silently-skipped webhook. This case is exercised by an automated test rather than the UI, since the UI's own payment-balance guard makes it awkward to reach by hand.

Coverage checklist

How the cases above map to Foodics' own "Accounting/ERP Integration" guide test cases:

Rounding amounts reflected correctlyCase C
Payment methods reflected/mapped correctlyCase A, B, H

Not covered by the mock tool: combos (products nested inside a Foodics combo) - the Mock POS Order UI only builds top-level product lines. The foodics.pos.order._line_vals_from_product() code path that flattens combo products is instead covered by an automated test, not a clickable mock scenario. If you need to click through a combo case by hand, the fastest way is a one-off Python snippet building a payload with a combos array (see the Foodics Orders API docs for the shape) and calling env['foodics.pos.order']._sync_from_payload(config, data) directly from an odoo-bin shell session.

Where to look: the accounting output

WhatWhere
The parsed Foodics order, its lines, payments, and raw payload Foodics > POS Orders
The generated invoice/credit note Accounting > Customer Invoices, or the smart button on the POS Order / the "Foodics Order" smart button on the invoice itself
The registered payments Accounting > Customer Payments, or the POS Order's Payments tab
The actual journal entry (debits/credits) Open the invoice or payment, then its "Journal Entry" smart button - standard Odoo accounting, nothing Foodics-specific about this part
Every inbound webhook call, processed or failed Foodics > Webhook Log (from foodics_base) - each row shows the event name, state, and (if it failed) the error

Troubleshooting / FAQ

I clicked a button and got a 404 with a plain "NOT FOUND" body.
That's not a Foodics-shaped error (those come back as JSON with a message key) - it means the URL didn't match any route at all. Almost always: the Odoo server process needs a restart to pick up a Python file change (see the warning box in Section 0).
"Sync Taxes"/"Pull Orders" says 401 Unauthenticated.
The Connection isn't authorized against the mock yet, or its access token doesn't match any Fake App - click "Authorize with Foodics" again.
Why doesn't fixing a Tax Mapping and clicking Retry regenerate the invoice lines?
By the time a total-mismatch is detected, the (draft) invoice already exists with whatever lines were built at that moment - regenerating it automatically would mean silently discarding a document a human might already be looking at or have started editing. Instead you fix the draft directly (it's still fully editable, nothing is posted yet) and post it yourself; Retry then picks up from there for the payment side. This is different from the payment-mapping case (Case H), where nothing about the already-posted invoice needs to change - only a new payment needs to be created - so Retry can do that part fully automatically.
Can I test against real Foodics after all this?
Yes - nothing about foodics_accounting changes. Follow the root README's "Switching to the real Foodics API later" section on the Connection record; Sync Taxes/Payment Methods/Pull Orders all route through the same foodics.config._get/_get_all helpers either way.
Does firing a mock webhook actually go over HTTP, or is it faked in Python?
Real HTTP - the Mock POS Order model does an actual POST to the Connection's Webhook URL, landing on foodics_base's real webhook controller, exactly like the genuine Foodics service would call it. That's deliberate: it means these test cases also exercise signature/lookup/dispatch code, not just the accounting logic itself.
