Foodics Base & Foodics Mock

What these two modules do, why they're split the way they are, and how the branch/product mapping actually works under the hood.

This covers foodics_base and foodics_mock. Order pushing/status-sync lives in a separate module, foodics_order_sync — see order_sync.html for a plain-language walkthrough of that one instead.

1. The shape of it

foodics_base

The reusable foundation. Owns the connection to Foodics, the OAuth login flow, branches, product mapping/approval, and a generic place for webhooks to land. Any future integration (accounting, purchase, inventory, ...) is meant to build on this, not duplicate it.

foodics_mock

A stand-in for the real Foodics servers, running inside your own Odoo. Same URLs shape, same OAuth dance, same response shapes - just fake data, so you can build and test everything before Foodics hands you real sandbox credentials.

Important: foodics_mock does not depend on foodics_base, and foodics_base does not depend on it either. They only ever talk to each other over plain HTTP, through the Custom API/Authorization Base URL fields on the Foodics Connection record - exactly the same way foodics_base would talk to the real Foodics. That means switching to production later is just: fill in real credentials, clear those two URL fields, and (optionally) uninstall foodics_mock. Nothing about foodics_base changes.

2. The Connection (OAuth)

One record, Foodics > Connection, holds everything needed to talk to one Foodics business account: environment (sandbox/production), your app's Client ID/Secret, and the access token once you've authorized. Clicking Authorize with Foodics opens Foodics' consent screen in a new tab; once approved, Foodics redirects back to /foodics/oauth/callback, which exchanges the code for an access token automatically. Every other button (Sync Branches, Sync Menu, ...) and every other module's API calls go through this one record's _get / _post helpers.

3. Branches: how Foodics and Odoo agree on a "place"

A Foodics Branch is a physical restaurant/store location: it has opening hours, a flag for whether it accepts online orders, and its own tax settings on Foodics' side. Odoo's closest equivalent to "a physical place stock moves in and out of, and sales happen at" is a Warehouse.

Foodics has no concept of your Odoo database, so it cannot tell us which warehouse a branch corresponds to - that's a judgment call only a human can make, once, the same way you decide which Odoo product a Foodics menu item really is. That's why, after clicking Sync Branches, each foodics.branch record shows up with its Foodics data filled in (name, reference, opening hours, "receives online orders") but its Odoo Warehouse field empty - you set that once, and it sticks across future syncs.

What that mapping is used for

  • When an order is pushed for a branch, its mapped Warehouse (if any) is copied onto the related Sale Order, so stock/reporting land in the right place.
  • A branch flagged "Receives Online Orders = No" on Foodics' side is never offered/used as a destination when sending an order - Foodics would reject it anyway.
  • A branch's Company is derived automatically from its mapped Warehouse (a Warehouse always belongs to exactly one Company in Odoo).

4. Product Mapping & the approval queue

Clicking Sync Menu pulls every product from Foodics and creates one Foodics Product Mapping row per item - always, whether or not it's approved yet. What happens next depends on one setting:

Settings > General Settings > FoodicsBehavior
"Foodics products require approval" ON (default) New items wait with status To Approve in Foodics > Product Mapping until someone clicks Approve (or Reject).
"Foodics products require approval" OFF New items are approved immediately - the matching Odoo product is created/linked as soon as the sync finishes, no human step in between.

What "approving" actually does

  1. It looks for an Odoo product whose Internal Reference (or, failing that, its barcode) matches the Foodics item's SKU.
  2. If one is found, that existing product is linked - no duplicate is created, and the mapping is marked "Matched Existing Product" so it's obvious later why no new product shows up.
  3. If none is found, a new product.product is created from the Foodics data.
  4. Either way, the resulting product gets is_foodics_product = True (shown as "From Foodics" on the product form) plus a link back to the mapping row that created it - so it is always obvious, on the product itself, that Foodics is the source.
On duplicates: two different Foodics items can never create two mapping rows for the same Foodics ID (enforced at the database level). And because approval always checks for a matching Odoo product first, if two Foodics items happen to share a SKU, the second one approved links to the product the first one created, instead of creating a second copy.

5. Webhooks: one door, many rooms

foodics_base exposes a single webhook URL per connection (/foodics/webhook/<secret>, shown on the Connection record). Every call Foodics makes to it - no matter the event - is saved first as a Foodics Webhook Log row, then dispatched by event name.

A module that cares about a specific event (say, foodics_order_sync caring about application.order.updated) reacts to it simply by inheriting foodics.webhook.log and adding a method called _handle_application_order_updated. foodics_base never needs to know that method, or that module, exists - which is the point: new integrations plug into webhooks without this module changing at all.

6. Using foodics_mock day to day

1

Create a Foodics Mock > Fake App - it's your stand-in for the developer app Foodics would otherwise create for you. It generates its own Client ID/Secret; you choose the Redirect URI.

2

On the real Foodics > Connection record, copy in that Client ID/Secret and Redirect URI, and point Custom API Base URL / Custom Authorization Base URL at the mock server's routes (/foodics_mock/v5 and /foodics_mock).

3

Authorize, sync branches/menu, map a warehouse and a product or two, and you have a fully working end-to-end setup with realistic (if fake) data.

4

Optional: paste the Connection's Webhook URL into the Fake App's Webhook URL field to also exercise foodics_order_sync's webhook handling and reconciliation cron - see order_sync.html.

5

When real credentials arrive: clear the two Custom ... Base URL fields, put in the real Client ID/Secret, re-authorize, and uninstall foodics_mock. Nothing else changes.
