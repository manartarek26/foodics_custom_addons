Testing the Full Cycle, Step by Step

Purchasing (foodics_purchase) and POS/accounting (foodics_accounting) together, on the same stock - suppliers, inventory items, purchase orders, receiving, returns to supplier, cost adjustments, and how a purchased item and a sold item meet on one Odoo product's stock card. Uses foodics_mock + foodics_mock_purchase_ext, no real Foodics account needed.

Read this first if you only want the short answer. The cycle is: Odoo is the source of truth for purchasing. A confirmed PO is pushed to Foodics as an approval request (draft/pending) - it never moves stock on either side. Only validating a receipt in Odoo moves stock (up) and pushes an Inventory Transaction (type 1, Purchasing) so Foodics' own levels move too; a return-to-supplier does the same in reverse (type 4). Foodics has no purchasing webhooks, so PO status/cost changes are polled on a cron. This is independent of foodics_accounting, which moves the same kind of stock the other direction (down) whenever a Foodics till closes or returns a sale. The two only stay consistent if (a) the branch's mapped warehouse is the same one POs receive into, and (b) a physical item sold via the till and bought via a PO resolve to the same Odoo product - both are now checked with non-blocking warnings, see Cases G and H below.
Known gap, as of this revision: foodics_accounting's POS sale/return does not currently move Odoo stock at all under Odoo's default "real time" POS stock setting - see the full explanation in Case I. The purchasing side (Cases A-G) is unaffected and moves stock correctly; this only concerns the till side.

0. One-time setup

Install foodics_base, foodics_mock, foodics_purchase and foodics_mock_purchase_ext (add foodics_accounting too if you'll run Case I). Then, if you haven't connected to the mock server at all yet:

  1. Create a Foodics Mock > Fake Apps record.
  2. Create a Foodics > Connection pointing its Custom API/Authorization Base URLs at the mock server, and authorize it.
  3. Copy the Connection's Webhook URL into the Fake App's Webhook URL field (needed if you'll also run the POS side in Case I).
  4. On the Connection, click Sync Branches, then open the branch and set Odoo Warehouse (Foodics > Branches). If you'll run Case I, also set Odoo POS Point there.

On the Connection's Foodics tab (added by foodics_purchase), set:

FieldSuggested test value
PO Creator ID (Foodics User) Any non-empty string, e.g. test-user-1 - the mock accepts anything, but the docs mark this required and _foodics_validate_for_push() blocks confirmation without it.
Auto-submit POs for review Off first (test Draft), on later (test Pending, Case B).
Receipt Price Tolerance %5 - to see Case J's price-deviation warning fire.
Auto-create products for new inventory items On - lets Case 1 create products for you instead of mapping by hand.
Apply cost adjustments to product costOn - needed for Case E to show an effect.
If you change any Python file in these modules (or pull an update that does), restart the Odoo server process first - controller/model code is only read once, at process start; editing a .py file on disk does not hot-reload, unlike views/data which a module upgrade does pick up.

2. Case A - the happy purchase path

Core Confirm in Odoo → pushed as an approval request, no stock yet

  1. Create a Purchase Order for the vendor linked to Hyper Market, one line: Tomatoes, qty 10 (order unit = box, matching the supplier pivot's order_to_storage_factor = 2 boxes→storage).
  2. On the Foodics tab, set Foodics Branch.
  3. Click Confirm Order.
Expect: confirmation succeeds, Foodics PO ID and Foodics Status = Draft (or Pending, if auto-submit is on) populate, and Sync State = Synced. Nothing moved in stock.quant yet - per the docs, a purchase order is only an approval request. Open Foodics > Purchase Sync Log (or the PO's View Sync Log) to see the POST /purchase_orders call and its response.

Core Receiving is what actually moves stock

  1. Open the PO's receipt (Purchase > Orders > (this PO) > Receipt smart button) and click Validate.
Expect: the picking's Foodics Sync State = Synced, Foodics TX ID populated. stock.quant for Tomatoes now shows +20 (10 boxes × factor 2 = 20 storage units) in the branch's mapped warehouse. Back on the PO, Foodics Status flipped to Closed automatically - the mock applied the same quantity_received/status logic the real platform uses (_apply_receiving_to_po()). Check Foodics Mock > Received Inventory Transactions for the posted type-1 "Purchasing" transaction with the converted storage quantity/cost.

3. Case B - approval simulation & status polling

Reliability Foodics has no PO webhooks - Odoo has to ask

The mock has no "Approve" button by design (mirroring that this normally happens in the real Foodics console, outside Odoo's control) - you simulate it by editing the mock record directly, the same way you'd simulate any other externally-driven change.

  1. Confirm a new PO as in Case A, but stop before validating the receipt.
  2. Open Foodics Mock > Received Purchase Orders, find the row matching your PO's Foodics PO ID, open it and change Status to 3 (Approved). Save.
  3. Back on the Connection, click Pull PO Statuses (or wait for the purchase-poll cron).
Expect: the Odoo PO's Foodics Status updates to Approved. Try status 4 (Declined) instead: the poll sets Sync State = Sync Error and logs a warning ("...was DECLINED in Foodics") visible in the Foodics tab's banner and the Sync Log - review before continuing, exactly like the accounting side's Needs Review pattern.

4. Case C - partial receipt / backorder

Reliability One transaction per picking

  1. Confirm a PO for 10 boxes of Cooking Oil.
  2. On the receipt, set Done quantity to 6 boxes and validate - choose Create Backorder when prompted.
Expect: the first picking pushes its own Inventory Transaction for the 6 received; the PO's Foodics Status becomes Partially Received. Validate the backorder picking for the remaining 4 - a second transaction is pushed, and the PO closes. Each Odoo picking maps to exactly one Foodics transaction, matching the doc's "partial deliveries naturally produce one transaction per validated picking" design.

5. Case D - return to supplier

Reversal Type 4, traced back through the original receipt

  1. Take an already-received PO from Case A. Open its receipt, click Return, confirm a return of some quantity.
  2. Validate the resulting outgoing picking.
Expect: stock decreases by the returned quantity; a type-4 "Return to Supplier" transaction is pushed, traced back to the original receipt/PO via origin_returned_move_id (_foodics_return_context()) - not by re-guessing the PO from the product alone. Visible under Foodics Mock > Received Inventory Transactions, type "Return to Supplier".

6. Case E - cost adjustments

Pull Foodics corrects a cost, Odoo picks it up on the next poll

  1. On the Connection, click Pull Cost Adjustments right after setup - the seeded CA-SEED-0001 (Cheese) is already there.
Expect: the Cheese foodics.inventory.item's Cost updates, and - because Apply cost adjustments to product cost is on - the linked product's Cost (standard_price) updates too, written with context={'disable_foodics_sync': True} so it doesn't loop back into any product-side sync.

7. Case F - stock levels pulled

Informational Foodics' own view of stock, side by side with Odoo's

  1. Click Pull Stock Levels after receiving something in Case A.
Expect: rows appear under Foodics > Stock Levels, one per (branch, item), showing Foodics' own quantity/ cost_per_unit. This is a read-only snapshot for comparison - it does not write into Odoo's stock.quant; if it drifts from Odoo's own on-hand quantity for the same product, that's a signal worth investigating (Foodics-side manual stock count, a transaction that failed to push, etc.), not something this pull auto-corrects.

8. Case G - branch/warehouse consistency (new)

Integration A PO should receive into the branch's own warehouse

  1. On a PO, set Foodics Branch to a branch mapped to Warehouse A.
  2. Confirm you see Deliver To (the PO's picking_type_id) auto-switch to Warehouse A's receiving type the moment you pick the branch.
  3. Now manually change Deliver To to a picking type belonging to a different warehouse.
Expect: a warning banner appears on the Foodics tab: "This PO receives into warehouse ..., but branch ... is mapped to warehouse ...". It does not block Confirm Order - some setups may deliberately cross-receive - but it's there so a mismatch is never silent. This is what stops PO receipts and POS sales for the same branch from quietly moving stock in two different warehouses.

9. Case H - sale/purchase product-mapping cross-check (new)

Integration Same SKU, two different Odoo products - now flagged

  1. Requires foodics_accounting or foodics_order_sync installed too (they own foodics.product.mapping). Sync the menu (Sync Menu) so at least one menu product exists.
  2. Pick a foodics.inventory.item and set its SKU to match a synced menu product's SKU exactly, but leave the two Linked Odoo Product/Odoo Product fields pointed at two different products (or leave one unmapped).
Expect: the inventory item's form shows a red banner ("Menu product ... shares this item's SKU ... but resolved to a different Odoo product...") and the list view highlights the row. Now set both Linked Odoo Product fields to the same product: the warning clears, and each side's Linked Menu Product / Linked Inventory Item field now points at the other mapping - a quick way to confirm, for any shared item, that a POS sale and a PO receipt of "the same thing" will actually move the same stock card. Most menu products (a "Burger") will correctly show no linked inventory item at all - only its raw ingredients would.

10. Case I - full cycle: buy it, then sell it

Known gap - the stock-quantity part of this case does not currently pass. foodics_accounting builds its pos.order records with a plain ORM create(), then calls action_pos_order_paid() / action_pos_order_invoice() directly - it never goes through _process_saved_order(). In core Odoo, a POS order's stock.picking is only ever created from _process_saved_order() or from one conditional call inside action_pos_order_invoice() that only fires when the company's stock policy is "At the session closing" and anglo-saxon accounting is on (pos_order.py, _should_create_picking_real_time()). Odoo's default company setting is "In real time" - under that default (and it's the common case), neither path ever runs here, so no stock movement happens for a sale or a return, not just the return. The financial side (invoice/credit note/payment reconciliation) is unaffected and already correct - see Section 9's step-by-step below with the stock checks removed. Fix, when ready: an explicit order._create_order_picking() call inside both _create_via_pos_order() and _create_via_pos_refund() in foodics_accounting/models/foodics_pos_order.py, right after action_pos_order_paid().

End to end One product, two directions, one stock card (financial side only, for now)

Requires foodics_accounting installed and its own setup done (Sales Journal, branch's Odoo POS Point, taxes/payment methods synced - see accounting_testing_guide.html). Pick a product that's both a purchase item and something the till can sell - easiest is to reuse Case H's merged mapping.

  1. Note the product's On Hand quantity (Inventory app) before starting - this is only to confirm the known gap above, not an expectation to pass yet.
  2. Buy it: confirm a PO for that item, receive it (Case A). On Hand goes up by the received storage quantity - the purchase side is standard purchase_stock, untouched by the gap above, and does move stock correctly.
  3. Sell it: build a Foodics Mock > Mock POS Orders order using the matching menu product, pay it, Close & Send.
Expect today: Foodics > POS Orders shows the sale Invoiced; Foodics > Purchase Orders shows the buy Closed; the sale's invoice and (on a return, see accounting_testing_guide.html Case F) the credit note are both correct and already Paid - no manual "Register Payment" step. On Hand will not move from the sale or the return until the gap above is fixed; only the purchase-side increase from step 2 will show.

11. Case J - failure paths

Defensive Bad data blocks confirmation, not silent guessing

ScenarioWhereExpect
Line's item has no Foodics Inventory Item mapped Confirm Order UserError listing every problem line before anything is pushed (_foodics_validate_for_push()) - PO stays in Draft.
Quantity below the supplier pivot's Minimum Order Quantity Confirm Order Same aggregate UserError, names the line and the MOQ.
No PO Creator ID set on the Connection Confirm Order Blocked - the docs require creator_id on every created PO.
PO currency differs from the Connection's business_currency Foodics tab Non-blocking warning banner - the docs don't define conversion behavior, so it's surfaced, not guessed.
Receiving at a cost differing from the PO line beyond the tolerance % After Validate on the receipt Non-blocking warning on the Sync Log entry; the transaction still posts.
A receipt line's product has no matching Foodics item at all After Validate That line is skipped with a logged warning rather than blocking the whole transaction push.
Reset to Draft a PO already pushed to Foodics PO form Blocked - "Cancel it first (which deletes/declines it upstream)".
Cancel a still-Draft-upstream PO PO form DELETE /purchase_orders/{id} - fully removed both sides.
Cancel a Pending/Approved PO PO form PUT status=4 (Declined) upstream instead of deleting.
Cancel a Closed PO PO form Refused with a logged warning - closed orders can't be touched per the docs' status table.

Where to look: the purchasing output

QuestionWhere
Did the PO reach Foodics? What did it send/get back? PO form > View Sync Log, or Foodics > Purchase Sync Log
Did stock actually move? Inventory > product > On Hand, or the picking's Moves tab

Is a mapping missing or inconsistent? Foodics > Inventory Items (red rows/banners), PO's Foodics tab (warning banners)

Troubleshooting / FAQ

The PO won't confirm - "no Foodics inventory item mapped".
Map Foodics Inventory Item on the order line (or sync inventory items first if the list is empty).
"Set 'PO Creator ID (Foodics User)' on the connection."
Any non-empty string works against the mock - the docs require it, they don't validate it's a real user id.
I edited the mock PO's status but nothing changed in Odoo.
Status changes made directly on the mock aren't pushed to Odoo (Foodics has no PO webhooks) - click Pull PO Statuses, or wait for the cron.
Receiving didn't push a transaction.
Only done moves tied to a purchase_line_id are included (_foodics_build_receipt_items) - check the move actually has a quantity done and belongs to this PO's line, and that the picking is picking_type_code == 'incoming'.
401 Unauthenticated calling any purchase endpoint.
Same root cause as the accounting guide's version of this: the Connection's stored access token doesn't match any foodics.mock.app - re-authorize.
I want to start the purchase-side seed data over.
Delete the Fake App's foodics.mock.inventory.item/ foodics.mock.supplier records - _ensure_purchase_seed() only seeds when the app has zero items, so removing them re-triggers it on the next sync.
